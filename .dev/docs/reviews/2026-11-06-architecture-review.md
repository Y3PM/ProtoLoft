## 结论

现有原生 PHP、SQLite、私有资源入口和领域路由适合这个项目，值得保留。当前需要在发布前收敛的是业务规则、状态与组件的实现来源：部分新增功能绕开了已有机制，已经造成可复现的越权、发错项目和失败后文件丢失。

用户确认：同名版本支持覆盖更新；MCP 未选项目默认覆盖权限内全部项目；不增加文件恢复、回收站或历史底稿保留；批注与分享按角色控制，不设置全站总开关。不能把这些已确认行为重新定义为待解决的产品问题。

随后根据用户指出的设置回退，已找到此前整文件恢复及旧模板重组的操作记录，并按 Gemini 原始差异恢复三处设置模板优化。证据、实际范围与本轮验证见 [设置优化恢复](2026-11-06-settings-recovery.md)。这也校正了仅凭现状将旧总开关解释为普通残留的不足：历史记录显示该模板经历过整文件回退与重组。

## 优先问题与边界校正

### F1 · 已修正 · 控制中心新建项目后的发布目标与版本状态

归一跟进：保存项目时同步发布选项；明确目标不存在时停止。发布回执复用首次渲染的版本展示字段，更新列表和数量，保留历史署名。Chrome 已覆盖新建后直接发版入口、发布后直接版本管理、同名覆盖数量不增加；以下为原问题证据。

位置：[admin.js:239](../../../assets/js/admin.js#L239)、[admin.js:891](../../../assets/js/admin.js#L891)。

场景：已有项目 A，在控制中心新建 B，不关闭控制中心，点击 B 行的“发布新版本”。创建成功只追加表格行，没有同步 `uploadItemSelect`。`openUploadModal(B, B名称)` 设置一个不存在的 option 后，回退到第一项 A，并将隐藏的发布目标改为 A；项目名称字段仍可显示 B。

本轮执行生产 `openUploadModal`，以原生 select 的无匹配选项语义构造上述状态，实测 `requested_item=33`、`actual_publish_item=11`、显示名称仍为新项目。没有在真实浏览器中提交错误版本；这里的证据是实际业务函数与受控 DOM。

根因：表格、发布下拉、侧栏、版本列表各自持有数据，创建成功后只修补局部 DOM。相同模式也出现在发布成功只改版本徽标/数量，版本管理继续读取旧 `data-versions` 的路径。

处理方向：创建/发布成功返回规范化实体，统一更新项目和版本数据，再由各视图消费；明确指定的发布对象不可因选项缺失而静默切到另一对象。验收应覆盖“新建后直接发布”“发版后直接进入版本管理”“同名替换不增加版本数量”。

边界：支持用户主动选择同名版本进行覆盖更新。本项指出的是目标从项目 B 错切到 A，不是同名覆盖本身。

### F2 · 已撤回 · MCP 未选项目默认表示权限内全部项目

位置：[mcp.js:23](../../../assets/js/mcp.js#L23)、[mcp.js:423](../../../assets/js/mcp.js#L423)、[mcp_access.php:128](../../../includes/mcp_access.php#L128)。

用户确认此行为符合产品要求。`project_id=0`、空 `project_ids` 表示当前账号权限内的全部项目；每次调用仍核验账号与对象权限。

原探针记录的 `[1]` → `[2,1]` 属于预期范围切换，不构成越权。本项撤回 P1 定级，不新增范围模式，不禁止空选择。探针已改为验证默认行为，不再按缺陷统计。

### F3 · P1 · 批注衍生接口绕过了版本范围与访客开关

位置：[annotations.php:28](../../../includes/actions/annotations.php#L28)、[annotations.php:31](../../../includes/actions/annotations.php#L31)、[collaboration.php:17](../../../includes/collaboration.php#L17)。

真实 HTTP 已复现两个结果：

- 访客只有 V2 的分享授权，直接请求 V1 批注被拒；但请求 `previous_annotations&ver_id=V2` 成功，返回 V1 的未解决批注正文。接口只检查当前版本，随后直接查询上一版本。
- `perm_guest_annotate=0` 时，访客请求当前版本的 `list_annotations` 被拒，但 `annotation_target` 仍返回完整批注及页面文字快照。详情定位没有复用访客批注访问限制；本次总开关移除后此观察仍可复现，尚未修改。

根因：资源访问、批注列表、定位详情和历史引用使用了不同的授权入口；验证源对象不等于授权返回的关联对象。

处理方向：集中批注读取策略，明确区分成员与分享访客，并对实际返回的每个版本核验授权。历史引用仅在合法范围内执行；`list/target/previous/review/carry` 应共享策略，而非分别追加条件。

### F4 · P2 · 现有 RP 写操作的失败结果与数据一致性

位置：[versions.php:207](../../../includes/actions/versions.php#L207)、[versions.php:247](../../../includes/actions/versions.php#L247)。

当前更换在事务开始前覆盖 `prototype.rp`；移除在事务中直接 `unlink` 文件。SQLite 回滚无法恢复文件。真实 HTTP 故障注入只在临时库增加拒绝 `rp_file` 更新的触发器，结果为：

- 更换接口返回失败，旧 RP 内容已被新内容覆盖。
- 移除接口返回失败，数据库仍指向 RP，文件已经不存在。

另外，两条路径读版本/项目和检查权限都早于最终写锁；未像 `version_publish` 一样，在锁内复核当前目标。与同时替换、删除、交接的竞争影响尚未执行，本报告不将其写成已复现。

根因：完整发布采用不可变目录→事务切换→退役清理，RP 新入口直接修改活动目录，形成第二套资产生命周期。

边界：支持成功覆盖和移除 RP，不增加面向用户的文件恢复、备份历史或回收站。本项仅记录现有请求返回失败时文件与数据库结果不一致的工程问题，不再列为新增恢复机制或发布前 P1。本次跟进不修改 RP 操作；如后续处理，也只校正单次写操作的一致性。

### F9 · P2 · 通知能力与界面判断不一致

## 架构取舍与建议保留的部分

- 原生 PHP+SQLite、免构建部署符合规模与使用方式；没有证据支持更换技术栈。
- `api.php` 的领域路由、私有 `asset.php`、不可变 `storage_dir`、同名替换代际校验、发布写锁内复核、删除事务中的退役登记，都是已存在且值得复用的机制。
- 版本署名快照、唯一 Owner 触发器、成员删除前项目检查、账号请求回查、MCP 哈希凭据和发布内凭据复核，分别处理了真实业务约束。
- 共享弹窗的焦点/背景管理与设置自动保存队列值得保留；继续扩大共用部分前应先修正相关模拟测试。
- 按本轮版本约定，上传者为受信内部成员，原型脚本同源以支持 Axure/批注。没有将缺少“不受信脚本沙箱”作为本项目缺陷。

既有取舍：交接负责人后，版本删除/覆盖仍按历史发布者判断；这与当前显式权限规则一致，署名快照也保持不变。本轮不调整版本覆盖能力，不扩展负责人对历史版本的操作权限。
